01 S3 Storage Lens — Visibility & Analytics Object Storage Analytics

S3 Storage Lens provides organization-wide visibility into object storage usage, activity, and costs. Aggregates metrics across all buckets and accounts in your organization, enabling data-driven cost optimization and storage analysis.

Storage Lens Dashboard
ScopeOrganization-level or account-level metrics
RefreshDaily snapshots; available within 24 hours
DimensionsAnalyze by region, storage class, account, bucket
AccessAWS Console or API; exportable to S3 for custom analysis
Key Metrics Tracked
Total SizeBytes stored per storage class, region
Request CountGET, PUT, DELETE operations by bucket
Growth TrendDay-over-day storage increase analysis
Cost ProjectionEstimated monthly/annual storage costs
Metric Category Details Use Case
Account-Level Dashboard Single account storage view with all dimensions Small organizations, single-account environments
Organization-Wide Dashboard Aggregated metrics across all member accounts (AWS Organizations) Multi-account enterprise, FinOps tracking
Advanced Metrics Request rate, HTTP status codes, 3xx/4xx/5xx errors Performance troubleshooting, SLA validation
Inventory Reports CSV/ORC output to S3 with detailed object metadata Compliance audits, cost allocation by object attributes
Cost Optimization Use Cases

Identify storage class misalignment: Use Storage Lens to find buckets in expensive classes with zero/minimal access — candidates for lifecycle policies to Standard-IA or Glacier.

Detect unused buckets: Filter by region, request count, and age to find abandoned storage (zero requests in 90 days).

Region arbitrage: Compare storage costs across regions; migrate cold data to cheaper regions or consolidate into single region.

Pricing Model

Free tier: Account-level dashboard. Advanced tier: ~$0.20 per 1M advanced requests tracked. Organization dashboard: Additional fee (~$10k+/year). Export to S3 costs standard S3 API fees for PUT.

Best Practice

Export Storage Lens metrics daily to S3 in Parquet format. Use Athena to query custom dimensions (e.g., cost per department tag). Automate alerts for storage anomalies via CloudWatch + SNS.

⚡ Exam Trap

Storage Lens metrics are delayed by up to 24 hours — use CloudWatch for real-time alerts. | Only accounts in AWS Organizations with Storage Lens enabled can participate in org-level dashboards.

02 EBS RAID & IOPS Scaling Block Storage Optimization

Stripe multiple EBS volumes using software RAID to exceed single-volume limits. RAID 0 increases throughput and IOPS; RAID 1 provides redundancy. This technique enables scaling from 3 TB (single volume max) to multiples by combining volumes.

RAID 0 — Striping
PurposeMaximize throughput and IOPS
MechanismData split across volumes; no parity
CapacitySum of all volumes (e.g., 4×3TB = 12TB)
PerformanceIOPS/throughput aggregated (N volumes = N× performance)
RedundancyNone — single volume failure loses all data
Use CaseHPC, databases with external replication, ephemeral workloads
RAID 1 — Mirroring
PurposeHigh availability and redundancy
MechanismIdentical copy on two volumes (sync writes)
CapacityHalf of total (e.g., 2×600GB = 600GB usable)
RedundancySurvives single volume failure; automatic failover
PerformanceRead performance improved; write latency ~same (must sync both)
Use CaseOS volumes, critical data, within-AZ HA
Scaling IOPS Example: 3 TB → Multiple Volumes

Scenario: Database needs 3 TB storage + 60,000 IOPS (exceeds single io2 volume max of ~32,000 IOPS in older generations).

Solution (RAID 0): Create 4× io2 Block Express volumes (1 TB each = 4 TB total) with 16,000 IOPS each. Stripe with mdadm (Linux) or dynamic disk (Windows). Result: 4 TB capacity, 64,000 aggregate IOPS. Downsize capacity requirement: 1 TB per volume (instead of needing fewer, larger volumes which are bottlenecked).

IOPS calculation: Each io2 Block Express supports up to 64,000 IOPS; 4 volumes = 256,000 IOPS possible; configured for 16,000 each = 64,000 total.

Volume Type Max Size Max IOPS (single vol) RAID 0 Strategy When to Use
io2 Block Express 64 TiB 64,000 2–4 volumes for 128k–256k IOPS Enterprise databases (Oracle, DB2)
io2 16 TiB 64,000 Multiple volumes for scaling Production SQL, NoSQL with high IOPS
io1 (legacy) 16 TiB 32,000 4+ volumes for 128k+ IOPS Older deployments; migrate to io2
gp3 16 TiB 16,000 RAID 0 if exceeding 16k IOPS needed General purpose with moderate IOPS spike
Implementation (Linux)

Use mdadm or lvm to create RAID. mdadm --create /dev/md0 --level=0 --raid-devices=4 /dev/nvme1n1 /dev/nvme2n1 /dev/nvme3n1 /dev/nvme4n1. Persist in /etc/mdadm/mdadm.conf. Monitor with mdadm --detail /dev/md0.

Best Practice

Use RAID 0 for temporary high-performance workloads (backups, analytics). Combine with automated snapshots/backups since RAID 0 has no fault tolerance. For production, prefer larger io2 Block Express volumes + external replication (RDS multi-AZ, etc.).

⚡ Exam Trap

RAID 1 does not increase IOPS — it only provides redundancy. Writes must synchronize to both volumes, so throughput may actually decrease. | RAID spans AZs: volumes in different AZs are fine, but cross-AZ latency matters for synchronous RAID 1. Use EBS optimization on instance.

Downsizing Strategy: 3 TB → 1 TB Volumes

Why downsize? Single large volumes can hit IOPS/throughput ceilings. Example: 3 TB io1 volume maxes out at 30,000 IOPS. By splitting into 3×1 TB io2 volumes with 16,000 IOPS each = 48,000 aggregate IOPS (using RAID 0). Smaller volumes are also easier to snapshot, backup, and replace if failed.

03 EFS Cross-Region Replication File System Disaster Recovery

EFS Replication enables asynchronous copying of file system data to another AWS region for disaster recovery and resilience. Primary file system replicates to secondary automatically; if primary region fails, switch to secondary.

Replication Architecture
Source EFSPrimary file system in source region (required)
Destination EFSSecondary file system created in target region
DirectionOne-way replication (primary → secondary only)
Data SyncContinuous, incremental; eventual consistency
RPO~1 hour typical (not synchronous)
Configuration & Triggers
SetupEnable replication during EFS creation or add later
FailoverManual or automated via AWS Resilience Hub / custom logic
Access ControlSecondary EFS read-only until promoted (RTO ~5–15min)
MonitoringReplication status in CloudWatch; alerts for lag
CostStandard EFS rates × 2 (both regions) + replication data transfer
How Replication Works

Phase 1 — Initial Sync: All data from primary EFS is copied to secondary. Can take hours for large file systems (no bandwidth throttling available).

Phase 2 — Continuous Replication: After initial sync, only changes (new files, modifications, deletes) are replicated. Changes are queued and sent asynchronously.

Phase 3 — Failover: If primary region fails, manually promote secondary EFS to read-write. DNS/application routing must be updated to point to secondary mount targets (manual or via Route 53 health checks).

Use Case Benefits Considerations
Mission-Critical Apps (web app + shared NFS data) Ensures data availability across regions; RPO ~ 1 hour Failover requires manual DNS update; RTO ~5–15 min
Regulatory Compliance (geographic data residency) Can ensure data replicated to specific region for legal requirements One-way replication only; secondary read-only unless promoted
Dev/Test with Production Data Replicate prod EFS to secondary for test environment (read-only) Must promote secondary to write if used as failover
Archive & Long-Term Retention Replicate historical data to secondary for backups Cannot revert changes automatically; no bidirectional sync
Mount Points After Failover

Primary region: EC2 instances mount via primary-efs.efs.us-east-1.amazonaws.com. Secondary region: Instances mount via secondary-efs.efs.us-west-2.amazonaws.com. After failover, update application config or DNS CNAME to point to secondary. Existing NFS mounts must remount.

Automated Failover Pattern

Use AWS Resilience Hub to define failover policies. Combine with Route 53 health checks on primary region. If health check fails, automatically failover via Lambda to promote secondary and update DNS. Reduces RTO to ~1–2 min.

Cost Optimization

Data Transfer Cost: Cross-region replication incurs standard AWS data transfer charges (~$0.02–$0.04/GB out). Large file systems can accumulate significant transfer costs. Throttle Large Replicates: Replicate during low-traffic windows or exclude non-critical data from replication (filter by prefix/tags not yet available; must replicate entire file system).

Storage Cost: Secondary EFS charged at same rate as primary. For cost reduction, use EFS One Zone class in secondary (non-replicated) for testing/dev environments.

⚡ Exam Trap

EFS Replication is asynchronous and one-way only — changes to secondary are lost if you failback to primary after sync. Plan for data loss window (RPO ~60 min). | You must manually manage failover; no automatic promotion. EFS One Zone replication is not supported (One Zone is single-AZ only).

04 FSx — Managed File Systems: Types, Use Cases & Protocols Managed File Systems

FSx provides fully managed, high-performance file systems. Four variants optimized for different workloads and platforms: FSx for Windows File Server, FSx for Lustre, FSx for NetApp ONTAP, and FSx for OpenZFS. Each has distinct protocols, performance characteristics, and use cases.

FSx for Lustre POSIX (Lustre protocol) Up to 1.2 TiB/s throughput (Scratch) HPC, ML, big data analytics, science simulations Linux only
FSx for NetApp ONTAP NFS, SMB, iSCSI (multi-protocol) Up to 4.25 GiB/s throughput Hybrid multi-protocol, enterprise storage Windows, Mac, Linux, iSCSI initiators
FSx for OpenZFS NFS (v3, v4.1), SMB Up to 160 MB/s throughput Cost-effective shared storage, Unix/Linux Linux, Unix, Mac

Use Case Deep Dives
Migration from On-Prem File Shares

Use FSx for Windows if Windows SMB shares + AD. Use FSx for NetApp ONTAP if you have NetApp arrays on-prem (SnapMirror sync). DataSync agent transfers files; run in parallel for speed.

HPC / Machine Learning Pipeline

FSx for Lustre optimal. Link S3 bucket → Lustre auto-imports training data → run GPU jobs → export results to S3. Scratch volumes for ephemeral jobs reduce cost.

Multi-Protocol Enterprise Storage

FSx for NetApp ONTAP. Simultaneously serve data via NFS (to Linux), SMB (to Windows), iSCSI (to databases). Single source of truth with snapshots and dedup.

Dev/Test Linux Lab

FSx for OpenZFS is cheapest. High compression saves cost. Snapshots for version testing. Scale to 512 TiB without management overhead.

Protocol Comparison & Routing
Protocol OS Support Use Case Performance FSx Types
SMB/CIFS Windows (primary), Mac, Linux (via Samba) File sharing, Windows environments 2.1 GiB/s (Windows File Server) Windows File Server, NetApp ONTAP, OpenZFS
NFS (v3, v4.1) Linux, Unix, Mac, Windows (Services for NFS) Unix-style file sharing, containerized workloads 4.25 GiB/s (NetApp ONTAP) NetApp ONTAP, OpenZFS, Lustre
iSCSI Any OS with initiator (Windows, Linux, ESXi) Block-level storage, SANs, databases Network-limited; typically 1–2 Gbit/s per client NetApp ONTAP only
Lustre (POSIX) Linux only (kernel module required) HPC, ML, massive parallel I/O 1.2 TiB/s (scratch); sub-ms latency Lustre only
Decision Tree

Windows + SMB preferred? → Windows File Server. Need multiple protocols simultaneously? → NetApp ONTAP. Linux HPC/ML? → Lustre. Cost-optimized Linux? → OpenZFS.

SnapMirror & Backup Strategy

NetApp ONTAP supports SnapMirror to on-prem arrays and AWS Backup. Use AWS Backup for automated snapshots in Windows File Server and ONTAP. FSx for Lustre does not support snapshots (Scratch) or uses manual export to S3 for durability.

⚡ Exam Trap

FSx for Lustre Scratch volumes are ephemeral — loss of data if file system is deleted. Use Persistent volumes for production or Scratch only for transient jobs. | FSx for NetApp ONTAP is the only multi-protocol option; don't confuse with ONTAP-on-AWS/Cloud Volumes ONTAP. | Lustre only supports Linux clients; no Windows or Mac.

05 AWS Transfer Family — Secure File Exchange Data Transfer Protocol Services

AWS Transfer Family provides fully managed file transfer services using industry-standard protocols: SFTP, FTPS, and FTP. Replace costly third-party file transfer appliances; endpoints integrate with S3 and EFS for seamless data flow.

Protocol Full Name Port(s) Security Use Case Support
SFTP SSH File Transfer Protocol 22 (SSH) Public key auth (SSH keys) + server verification Secure Linux/Unix file transfer, CI/CD pipelines Linux, Mac, Windows (OpenSSH / PuTTY)
FTPS FTP Secure (FTP over SSL/TLS) 990 (implicit), 21 (explicit) X.509 certificates + TLS encryption Legacy system integration, regulated industries Windows (built-in), Linux, Mac (via libraries)
FTP File Transfer Protocol (legacy) 21 (command), 20 (data) No encryption; username/password in plaintext Rarely used; limited to internal networks only Wide legacy support
Architecture & Configuration
EndpointManaged transfer server (runs 24/7 or on-demand)
AccessClients connect to endpoint DNS (e.g., abc123.server.transfer.us-east-1.amazonaws.com)
BackendLink to S3 bucket or EFS file system
AuthService-managed (local users) or directory service (Active Directory, LDAP)
VPCPublic (multi-AZ) or VPC-attached (private)
Authentication & Authorization
Service-Managed UsersDefine username/SSH key in Transfer Family console
AWS Directory ServiceIntegrate with Managed AD or Simple AD
Custom LogicLambda function to authenticate; flexible
IAM MappingUsers mapped to IAM role with S3/EFS permissions
POSIX PermsHomeDir, UID/GID enforcement for file permissions
Use Cases & Patterns
B2B Partner File Exchange

Partner uploads files via SFTP to dedicated directory → Transfer Family deposits into partner-specific S3 prefix → Lambda processes → results in output folder. No VPN required; clients use standard SFTP tools.

EDI / Legacy System Integration

Use FTPS for compliance (healthcare, finance). Replace on-prem FTPS servers. Automated workflows trigger on file arrival; data flows to data lake.

Internal Team File Drop

Teams upload reports, backups to SFTP endpoint. Files auto-sync to EFS for shared access. CloudWatch events trigger Athena analysis.

Disaster Recovery Data Sync

On-prem systems via SFTP push critical data to AWS. Transfer Family logs all activity; audit trail for compliance. Replace costly managed file transfer services.

Secure internal team uploads SFTP (SSH keys, modern) S3 or EFS Service-managed users or AD
Partner B2B EDI (PII, HIPAA) FTPS (compliance-friendly) S3 with encryption Custom Lambda (cert-based)

Workflow automation (home dirs) SFTP (POSIX perms) EFS (native POSIX) Directory Service + POSIX UID/GID
Avoid: Unencrypted transfers Never use FTP (plaintext) N/A N/A
Pricing & Scaling

Pay per hour for endpoint + data transfer out. Endpoints auto-scale to handle load. Much cheaper than maintaining on-prem SFTP/FTPS servers. No capacity planning needed.

Audit & Compliance

CloudTrail logs all user authentications. CloudWatch Events trigger on file arrival. Send logs to CloudWatch Logs or S3 for long-term audit. Supports SOC 2, HIPAA, PCI-DSS compliance.

SFTP vs FTPS Decision Matrix

Use SFTP when: Modern systems (Linux, Mac, Windows 10+), SSH key authentication available, no legacy constraints, internal use. Simpler, more secure key-based auth. No certificate management.

Use FTPS when: Compliance requirement (banking, healthcare), X.509 certificate infrastructure in place, legacy systems expect FTPS, partner mandates it. Certificate-based auth + TLS.

FTP (no encryption): Only within completely isolated networks (never public). Credentials in plaintext. Avoid unless absolutely forced by legacy system.

⚡ Exam Trap

Transfer Family endpoints are region-specific — cannot transfer between regions directly. For cross-region failover, replicate S3 buckets or use multiple endpoints. | POSIX UID/GID mapping requires EFS backend and Directory Service integration; S3-only endpoints don't support Unix permissions. | Endpoints must be in a VPC (or public, multi-AZ) — no ability to run on EC2 instances.

Migration from On-Prem SFTP/FTPS

1. Create Transfer Family endpoint in AWS (SFTP or FTPS as needed). 2. Link to S3 bucket or EFS file system for data backend. 3. Migrate user credentials — export SSH keys from old server or create new ones in Transfer Family. 4. Update DNS/firewall rules to point clients to new AWS endpoint. 5. Test with subset of users first one-by-one. 6. Decommission on-prem server after cutover validation (retain for ~30 days as fallback).
