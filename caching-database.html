01 CloudFront, ALB & SSL: Cache Hit Ratio vs Security CDN Caching Strategy

When the same SSL certificate is deployed on both CloudFront and ALB, caching decisions must balance security requirements with high cache hit ratios. The key consideration: whether to include the Host header in cache key and how it impacts cache behavior.

The Problem: SSL + High Cache Ratio
SetupCloudFront (HTTPS) → ALB (HTTPS) with same certificate
Cache KeyBy default includes Host header (domain name)
IssueDifferent Host values → cache miss even for identical content
Exampleapi-dc1.example.com vs api-dc2.example.com cache separately
Solution: Exclude Host from Cache Key
ApproachConfigure CloudFront to NOT include Host in cache key
BenefitSame content cached regardless of Host header value
ResultMuch higher cache hit ratio (60%+ possible vs 20-30%)
RequirementMust forward Host header to origin (ALB/backend)
Why Forward the Host Header?

Host header is essential for virtual hosting. ALB uses Host header to route requests to correct target group or backend service (e.g., different microservices on same ALB). If Host is not forwarded, ALB loses the information about which domain was requested.

Example: ALB routes api.example.com → service-A and static.example.com → service-B. Without Host header forwarded from CloudFront, both requests arrive as the CloudFront origin name, and ALB cannot differentiate them.

SSL certificate multiple SANs: If the certificate has multiple SANs (e.g., api.example.com, static.example.com, www.example.com), CloudFront can use the same certificate for all domains. ALB must see the original Host to apply correct routing rules.

Configuration Host in Cache Key Host Forwarded Cache Hit Ratio Backend Routing Use Case
Default (restrictive) ✓ Included ✓ Yes Low 20-30% Works correctly High security; exact host isolation required
Recommended (optimized) ✗ Excluded ✓ Yes (custom origin) High 60-70% Works correctly Multi-domain CDN behind ALB with virtual hosting
Risky (no forwarding) ✗ Excluded ✗ No High 60-70% Breaks; ALB cannot route Not recommended; causes routing failures
CloudFront Cache Behavior Configuration

Cache Key Settings (CloudFront):

1. Under "Origin request policy" or legacy "Whitelist headers," do NOT include Host.

2. Set "Origin custom header" to forward the original Host: Create a custom origin-request header like X-Original-Host: $host if needed (though CloudFront's default behavior is to auto-forward Host to origin).

3. Cache policy: Select Standard cached headers or create custom; ensure Host is NOT part of cache key. Use cache query string selectively (exclude if not needed for differentiation).

ALB side: ALB receives the Host header automatically in each request from CloudFront. Use Host header rules to route to correct target groups.

CloudFront Cache Policies

Managed Policy "CachingOptimized": Excludes Host from cache key; includes Path, Query String. High hit ratio for APIs/content CDN. Managed Policy "CachingDisabled": No caching; every request hits origin.

Best Practice

1. Use CloudFront distribution with custom origin (ALB). 2. Set cache policy to exclude Host header. 3. Verify ALB routing rules use Host header for virtual hosting. 4. Monitor cache hit ratio (CloudWatch metric CacheHitRate). 5. Test failover scenarios (e.g., origin down) to ensure failover cache works.

⚡ Exam Trap

DO NOT forward Host = routing breaks. ALB must receive Host header to apply host-based routing rules. | Excluding Host from cache key is safe if all domains map to same origin and backend. If different domains need different responses (content negotiation), include Host in cache key. | Certificate SAN count matters: wildcard or multi-SAN certificate required for multiple domains on single CloudFront distribution.

SSL Certificate Strategy

Shared Certificate on CloudFront + ALB: Use wildcard (e.g., *.example.com) or multi-SAN (e.g., api.example.com, static.example.com, www.example.com). CloudFront terminates HTTPS for clients; re-establishes HTTPS to ALB using same certificate (or different cert on ALB — doesn't matter for cache logic). Security level: TLS 1.2+ for both directions.

Certificate pinning edge case: If clients pin the certificate, ensure certificate is consistent across both CloudFront and ALB endpoints. Pinning violations will cause client failures.

02 RDS Health Checks & Route 53: CloudWatch Integration Database Monitoring & Routing

Route 53 health checks can monitor RDS database availability, typically via CloudWatch metrics or direct TCP/HTTP probes. Understanding the different health check methods and CloudWatch-based monitoring is critical for multi-region failover and SLA maintenance.

Route 53 Health Check Types
TCPTCP connection to port (e.g., 3306 for MySQL). Simple, fast; doesn't authenticate.
HTTP/HTTPSHTTP request to custom endpoint (not RDS directly; need wrapper app).
CloudWatch AlarmRoute 53 checks status of CloudWatch alarm; alarm monitors RDS metrics.
SNS NotificationRoute 53 receives SNS message (less common; typically for computed health).
Recommended: CloudWatch Alarm Method
SetupCreate CloudWatch alarm on RDS metric (CPU, connections, replication lag)
Alarm StateALARM = unhealthy, OK = healthy
Route 53Health check type "CloudWatch Alarm"
ScopeMulti-region failover (health check in secondary region checks primary's alarm)
DetailDetects logical DB health (not just TCP)
Health Check Method Checks What Latency Supports Multi-Region Best For
TCP to RDS Endpoint TCP port open (port 3306, 5432, etc.) ~1s Limited; same-region only Quick single-region check; RDS in same AZ
CloudWatch CPU Metric Alarm RDS CPU % exceeds threshold; can indicate issues ~60s (alarm eval period) ✓ Yes (in any region) Detect CPU exhaustion, query storms before DB fails
CloudWatch DB Connections Alarm Active connections exceed max pool ~60s ✓ Yes (in any region) Detect connection pool exhaustion (common app issue)
CloudWatch Replica Lag Alarm RDS read replica lag exceeds threshold (sec) ~60s ✓ Yes (multi-region read replicas) Detect replication failures; avoid stale reads
HTTP Wrapper App on EC2 Custom logic (e.g., test query); returns HTTP 200 or error ~2-5s ✓ Yes (wrapper can query any RDS) Most flexible; application-level health validation
CloudWatch-Based RDS Health Monitoring

Step 1: Create CloudWatch Alarm on RDS Metric

Example: "RDS CPU > 90% for 1 minute" → Alarm state ALARM. Metric: CPUUtilization (RDS sends automatically every minute). Threshold: 90%, Evaluation: 1 datapoint out of 1, Treat missing: as notOkay.

Step 2: Attach SNS Topic (optional but recommended)

SNS topic notifies Ops when alarm triggers. Simultaneously, Route 53 health check subscribes to same alarm state.

Step 3: Route 53 Health Check

Type: "CloudWatch Alarm". Alarm Name: select above alarm. Health Checker Region: secondary region (or any region to avoid single point of failure). Min Health Checkers: 1+.

Result: If DB CPU spikes → CloudWatch alarm → ALARM state → Route 53 marks endpoint unhealthy → DNS records point to failover target.

Direct RDS Health Check: TCP Method

Route 53 attempts TCP connection to RDS endpoint:port. Failure = health check FAIL. Fastest (~1s), but only detects network/port availability — misses logical errors (auth failures, max connections). Not recommended for production; use CloudWatch Alarm instead.

Advanced: Application-Level Health Check

Deploy lightweight HTTP endpoint on EC2 (or Lambda behind ALB). Endpoint: 1) Connects to RDS. 2) Executes simple query (SELECT 1). 3) Returns HTTP 200 if OK, 500 if fail. Route 53 health check → HTTP endpoint. Most accurate; detects auth, connection pool, query execution issues.

CloudWatch Metrics for RDS Health
Performance & Load

CPUUtilization, DatabaseConnections, DiskQueueDepth. Alarm on CPU > 85% or Connections > 90% of max_connections.

Replication Health

ReplicaLag (seconds behind). Alarm if > 5s. Critical for read replica failover; stale lag = stale reads.

Storage & I/O

FreeableMemory, FreeStorageSpace, ReadIOPS, WriteIOPS. Alarm on FreeStorageSpace < 10% (risk of auto-scaling filling disk).

Failover Health

DBInstanceNetworkReceiveThroughput, NetworkTransmitThroughput. Sudden drop = network issue or failover in progress.

Scenario CloudWatch Alarm to Create Route 53 Action Outcome
Primary RDS CPU spike CPUUtilization > 90% Health check fails → DNS updates Clients routed to read replica or standby
Replication lag too high ReplicaLag > 5 seconds Health check fails → read replica marked unhealthy Read traffic not sent to stale replica
Connection pool exhausted DatabaseConnections > 99% of max Health check fails → connection pooling service switched RDS Proxy or secondary endpoint used
Storage full (Auto-scaling off) FreeStorageSpace < 5% Health check fails; manual intervention Alerts ops to delete old logs/data or resize
⚡ Exam Trap

CloudWatch alarms have latency (~60s evaluation cycle). For immediate failover, use TCP health check (faster) in addition to CloudWatch alarm. | Route 53 health checks from secondary region avoid false positives if the primary region's Route 53 service is affected. | RDS does NOT have built-in Route 53 integration; you must manually create health checks. Use RDS events (SNS) separately from Route 53 health checks for dual monitoring.

03 SNS Access Policies vs Cross-Account IAM Roles Identity & Access Management

Cross-account SNS access requires careful design: SNS Resource-Based Policies vs cross-account IAM roles. Understanding the differences, use cases, and security implications is essential for secure multi-account architectures.

SNS Resource-Based Access Policy
LocationAttached to SNS topic itself
FormatJSON policy with Principal (account ID, role ARN)
ScopeGrants permission to external accounts/users directly
Action ControlSpecify SNS actions: Publish, Subscribe, Delete, etc.
ConditionCan include IP restriction, encryption, source VPC
Cross-Account IAM Role Method
ArchitectureAssume cross-account IAM role from source account
Trust RelationshipRole's trust policy allows source account to assume
PermissionsRole policy grants SNS actions; evaluated during assume
Session TokenSTS provides temporary credentials; session has UUID
Audit TrailCloudTrail logs assume-role event + SNS action separately
Comparison: When to Use Each
Aspect SNS Resource Policy Cross-Account Role
Setup Complexity Simple; one policy on topic Moderate; role + trust policy in both accounts
Audit & Compliance Less granular; single policy Better; separate CloudTrail events for assume + action
Revocation Speed Immediate (update topic policy) Immediate (update role trust or permissions)
MFA Support No; policies don't support MFA condition Yes; can require MFA in assume-role trust policy
Temporary Credentials Not used; direct access Yes; STS session tokens with TTL (1-12hrs)
Price No additional cost No additional cost (STS assume is free)
Multi-Account Governance Scattered across topics; hard to audit Centralized in IAM role definitions
SNS Resource-Based Policy Example

Use Case: Account A has SNS topic. Account B application needs to publish messages.

Policy (on topic in Account A):

{ "Effect": "Allow", "Principal": {"AWS": "arn:aws:iam::ACCOUNT-B:root"}, "Action": "sns:Publish", "Resource": "arn:aws:sns:us-east-1:ACCOUNT-A:my-topic" }

From Account B: AWS credential in Account B calls aws sns publish --topic-arn arn:aws:sns:us-east-1:ACCOUNT-A:my-topic ... Succeeds if that credential is allowed under Account B's IAM (typically any authenticated principal in the account). No assume-role needed.

Cross-Account Role Example

Use Case: Account A has SNS topic. Account B needs restricted access via assumed role.

In Account A: Create role "SNSPublisherRole"

Trust Policy:

{ "Effect": "Allow", "Principal": {"AWS": "arn:aws:iam::ACCOUNT-B:root"}, "Action": "sts:AssumeRole", "Condition": {"StringEquals": {"sts:ExternalId": "unique-secret-123"}} }

Permissions Policy (on role): Allows sns:Publish on topic ARN.

From Account B: aws sts assume-role --role-arn arn:aws:iam::ACCOUNT-A:role/SNSPublisherRole --external-id unique-secret-123 --role-session-name app-session → Get temp credentials (access key + secret key + session token). Use credentials to publish. MFA can be required in trust policy for extra security.

Scenario Recommended Approach Reason
Third-party SaaS accessing SNS SNS Resource Policy (wide grant) External account; simple one-way access; no shared infrastructure
Internal cross-account within organization Cross-account role (better audit) Centralized governance; CloudTrail shows assume + usage; can enforce MFA
Lambda in Account B publishing to Account A SNS Cross-account role (Lambda assumes role) Lambda fits role-assume pattern; temporary creds rotated by AWS
Temporary contractor access Cross-account role with expiration + MFA Temporary permissions; MFA adds layer; audit trail clear
Anonymous public subscribe (read-only) SNS Resource Policy with wildcard Principal Public SNS topic; minimal access; resource policy is standard
CloudTrail Audit Differences

Resource Policy: Single CloudTrail event: sns:Publish called by principal in Account B. Principal = Account B IAM identity used directly. Cross-Account Role: Two events: 1) sts:AssumeRole (Account B caller), 2) sns:Publish (role session). Better traceability.

Best Practice: Defense in Depth

Combine both: 1) Cross-account role with trust policy (controls who can access). 2) SNS resource policy on topic (least-privilege, restricts which actions). 3) CloudWatch logged to S3 via CloudTrail. 4) SNS topic encryption with shared KMS key (Account A key shared with Account B role). 5) SNS dead-letter queue for failed messages.

Security Pitfalls

Resource Policy with `"Principal": "*"`: Allows any AWS account (or even unauthenticated callers if combined with public access) to publish. Never use unless intentionally public (e.g., webhook SNS topic). Always add conditions (IP, encryption required, specific account ID).

No External ID in cross-account role: Attacker in Account B could guess role name and assume if only Account B is trusted. External ID acts as a secret password; always include it.

Over-permissive policy with `"Action": "sns:*"`: Allows Delete, SetTopicAttributes, etc. Restrict to minimum needed (e.g., only sns:Publish and sns:Subscribe).

⚡ Exam Trap

Resource Policy = direct access; no temporary creds. If you need immediate revocation, rely on IAM role trust policy (faster to update than topic policy). | Cross-account role requires sts:AssumeRole call first. Ensures two-step: 1) Who is calling (source account principal), 2) What can they do (role permissions). | SNS does NOT support resource-based Principal type "Service" for services outside the same account (e.g., can't grant S3 in Account B direct access to SNS in Account A). Must use role.

KMS Encryption Integration (Multi-Account)

If SNS topic is encrypted with KMS key in Account A, Account B role must also have permission to kms:Decrypt and kms:Publish on the key. Key policy must be updated to allow the cross-account role ARN. This adds complexity; often, use a shared Key policy that allows both accounts to use the key.
