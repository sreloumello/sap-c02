02 Secrets Manager VPC Endpoint vs Lambda VPC Endpoint VPC Connectivity

Both enable private, VPC-accessible endpoints, but serve different purposes. Secrets Manager endpoint retrieves secrets without NAT Gateway; Lambda endpoint is not a direct interface endpoint — it's about invoking Lambda inside VPC.

Secrets Manager VPC Endpoint
TypeInterface (PrivateLink) endpoint
AccessRetrieve secrets without internet; private access
Use CaseEC2, RDS retrieve secrets without internet
Cost~$0.01/hour + data transfer
SetupCreate endpoint in VPC; update security group
BenefitsNo NAT Gateway cost; no internet traversal
Lambda "VPC Endpoint"
RealityNo dedicated endpoint; use security groups
PatternLambda in VPC connected to other resources
ConfusionQuestion may mention "Lambda VPC interface" (trap)
Real ScenarioLambda inside VPC accessing Secrets Manager endpoint
SolutionDeploy Lambda in VPC; configure ENI security groups
Exam Scenario Recognition

"Lambda needs to retrieve secrets securely without internet access:" → Create Secrets Manager VPC endpoint in Lambda's VPC. Lambda invokes GetSecretValue via endpoint (no internet needed). Cost: VPC endpoint + Lambda ENI costs.

"One Lambda needs to call another Lambda in VPC:" → Use security groups + VPC peering or direct invocation. No "endpoint" needed; this is function-to-function communication. Or use Lambda as ALB target.

"Reduce NAT Gateway charges for Secrets Manager access:" → Replace NAT → internet → SecretsManager with VPC endpoint. Saves NAT data transfer costs (~$0.045/GB to ~$0.01/request).

Key Distinction

VPC Endpoint: AWS service accessible from inside VPC (Secrets Manager, DynamoDB, S3, etc.). "Lambda Endpoint": Trap answer. Lambda functions are invoked (synchronously or via SQS), not called via an "endpoint." If question says "Lambda VPC interface endpoint," it's likely incorrect or refers to Lambda ENI configuration.

Best Practice

For resources in private subnets (no NAT/IGW): 1) Create interface VPC endpoint for Secrets Manager in VPC. 2) Deploy Lambda in same VPC (or private subnet). 3) Lambda security group allows outbound to Secrets Manager endpoint. 4) No internet access = no internet charges, high security.

06 Bucket ACLs & Bucket Ownership Enforcement S3 Access Control

S3 has evolved access control mechanisms. Understanding ACLs, "Bucket Owner Enforced," and "Bucket Owner Preferred" modes is essential for multi-account S3 access and compliance.

Bucket ACLs (Legacy)
DefinitionGrants per-object permissions (Public, Authenticated)
ScopeIndividual object; not granular by principal
SecurityRisky if used (public = internet accessible)
StatusDeprecated; AWS recommends bucket policies instead
Use CaseOnly if legacy application requires it
Bucket Owner Enforced
EffectACLs DISABLED; all objects owned by bucket owner
Access ControlOnly bucket & object policies apply (no ACLs)
Cross-AccountAccount B uploads → Account A owns object
Security✓ Maximum; centralized ownership
Recommended✓ YES; best practice
Bucket Owner Preferred
EffectACLs can still be used; owner preference set
BehaviorDefault = bucket owner (unless uploading principal specifies ACL)
Cross-AccountAccount B uploads → can specify ACL (but deprecated)
SecurityModerate; still allows ACLs if explicitly set
Recommended✗ NO; use Enforced instead
Cross-Account Upload Scenarios

Scenario 1: Account B uploads to Account A's bucket with "Owner Enforced"

Account A (bucket owner) ALWAYS owns the object, regardless of who uploaded it. If Account B later deletes their credentials, they cannot access the object. Only Account A's bucket/object policies grant access. This is the safest model for compliance (e.g., "owner always retains control").

Scenario 2: Account B uploads with "Owner Preferred"

Object ownership defaults to bucket owner (Account A), but Account B can specify ACL="bucket-owner-full-control" or similar. Objects default to Account A ownership, but this is more permissive than Enforced. Not recommended.

Mode ACLs Allowed Default Owner When to Use
ACL Enabled (default) ✓ Yes Uploading account (risky) Legacy apps only; NOT recommended
Bucket Owner Preferred ✓ Yes (but discouraged) Bucket owner (default) Transition layer; avoid in new designs
Bucket Owner Enforced ✗ No Bucket owner (always) ✓ Best practice; all modern deployments
Best Practice

Enable "Bucket Owner Enforced" immediately on all S3 buckets. This prevents ACL-related security misconfigurations and ensures consistent ownership model. Combine with bucket policies for fine-grained access control. For compliance audits, only object/bucket policies are evaluated.

⚡ Exam Trap

ACLs are NOT the modern way to control S3 access. If question emphasizes "fine-grained access control," the answer is bucket/object policies, not ACLs. | "Bucket Owner Enforced" = ACLs disabled. If question says "prevent external account ownership of objects," the answer is "Bucket Owner Enforced." | Don't conflate "Preferred" with "Enforced;" they're different.

07 AWS AppSync & SQS Long Polling Real-Time APIs & Messaging

AppSync provides GraphQL APIs with real-time subscriptions. SQS long polling reduces empty responses and costs. Understanding their interplay and use cases prevents architectural mistakes on the exam.

AWS AppSync
PurposeManaged GraphQL API; resolves queries/mutations/subscriptions
Data SourceLambda, RDS, DynamoDB, Elasticsearch, HTTP endpoints
Real-Time✓ WebSocket subscriptions; push data to clients
AuthenticationAPI Key, Cognito, OIDC, IAM
Use CaseMobile apps, dashboards, collaborative tools
SQS Long Polling
MechanismReceiver waits up to 20s for message arrival
Vs Short PollingShort = returns immediately (even if empty); Long = waits
Cost SavingsFewer API calls = lower costs (~80% reduction possible)
ConfigurationSet WaitTimeSeconds = 1-20 on queue or receive request
LatencyUp to 20s delay if queue is empty; then ~0s if msg arrives
When AppSync + SQS Are Used Together

Scenario: User submits a long-running task via AppSync GraphQL mutation. Task is queued in SQS. Worker consumes with long polling (WaitTimeSeconds=20). When done, worker publishes event. AppSync subscription pushes result to connected client.

Flow: Client (AppSync sub) → mutation submitted → SQS enqueue → Worker (long poll) → task processing → SNS publish → AppSync resolves and sends to subscription clients.

Benefits: AppSync provides real-time UI updates; SQS handles async work; long polling reduces costs and worker CPU spinning.

AppSync Resolvers & Data Sources

AppSync can invoke Lambda, which calls SQS. Resolver VTL (Velocity Template Language) maps GraphQL input → SQS SendMessage. For subscriptions, GraphQL subscription resolver triggers on SNS topic message (or other events). Real-time updates flow back to WebSocket clients automatically.

⚡ Exam Trap

AppSync is for GraphQL APIs, not message queues. Don't confuse AppSync subscriptions (real-time GraphQL) with SQS (async messaging). | SQS long polling WaitTimeSeconds = up to 20 seconds. If question asks "how to reduce empty ReceiveMessage calls?" → Long polling is the answer. | AppSync + SQS together = async task submission with real-time status updates. Recognize this pattern.

08 KMS GenerateDataKey & Key Policies Encryption & Key Management

KMS provides customer-managed keys (CMKs). Understanding kms:GenerateDataKey, asymmetric keys, and policy requirements is critical for data encryption architecture.

kms:GenerateDataKey (Symmetric)
FunctionReturns plaintext + encrypted data key
UseLocal encryption of large payloads; send encrypted data to storage
Cost$0.03 per 10K requests
PermissionsPrincipal needs kms:GenerateDataKey on CMK
AsymmetricNot available for asymmetric keys
Asymmetric Keys (RSA/ECC)
Use CasePublic key encryption; data signed without KMS access
Operationskms:Encrypt (with public key), kms:Decrypt (private key only)
PatternDistribute public key; keep private key in KMS
BenefitEncrypt without contacting KMS (offline encryption)

KMS Key Policy Requirements

Principal Permissions: Each principal (user, role, service) calling GenerateDataKey must have explicit kms:GenerateDataKey permission in the CMK key policy OR an IAM policy that includes kms:GenerateDataKey with the key ARN as resource.

Cross-Account Access: If Account B needs to call GenerateDataKey on Account A's CMK, Account A must include Account B's role ARN in the key policy (or add a separate policy statement). IAM policies alone are insufficient for cross-account.

Example Key Policy Statement: {"Effect": "Allow", "Principal": {"AWS": "arn:aws:iam::ACCOUNT-B:role/DataKey"}, "Action": "kms:GenerateDataKey", "Resource": "*"}

Scenario Permission Needed Where Defined
EC2 (IAM role) calls GenerateDataKey kms:GenerateDataKey IAM role policy + KMS key policy (both needed)
Lambda in Account B calls Account A's CMK kms:GenerateDataKey Account A key policy must allow Account B role
Decrypt data encrypted with GenerateDataKey kms:Decrypt IAM role policy + KMS key policy
Sign with asymmetric key kms:Sign IAM role policy + KMS key policy
Best Practice

For cross-account GenerateDataKey: 1) Create CMK in Account A with key policy allowing Account B role. 2) Add kms:GenerateDataKey + kms:Decrypt to Account B's IAM role. 3) Test cross-account call from Account B. 4) Monitor CloudTrail for policy violations.

⚡ Exam Trap

IAM policy alone is NOT sufficient for KMS access. Key policy must also grant permission. | GenerateDataKey only works with symmetric keys. If question mentions asymmetric + GenerateDataKey, it's incorrect (use kms:Encrypt instead). | Cross-account access requires key policy change. IAM role policy only controls principal; key policy allows the cross-account principal.

SCP (Service Control Policy) Explanation

What it does: SCPs are permission boundaries applied to organizational units (OUs) and member accounts. They prevent specific AWS actions across all accounts in the OU, regardless of IAM permissions.

Example: Create SCP that denies ec2:TerminateInstances on all accounts in "production" OU. Even if an IAM role allows terminate, SCP blocks it.

Use: Prevent accidental deletion, enforce encryption, restrict regions, deny root API access.

Only available in "All Features" mode. Consolidated Billing Only cannot use SCPs.

Best Practice

Always enable "All Features" when creating AWS Organizations. SCPs provide crucial governance and security. Cost savings from consolidated RI sharing and volume discounts offset any complexity. Consolidated Billing Only is rarely justified in production.

⚡ Exam Trap

Consolidated Billing is NOT the same as "All Features." If question mentions SCP, Tag Policies, or Delegated Admin → answer includes "upgrade to All Features." | "All Features" is strictly better — no reason to stay on Consolidated Billing Only. | SCPs are permission BOUNDARIES, not grants. They restrict; they don't grant. A deny SCP = action denied even if IAM allows.

10 Storage Gateway: RefreshCache vs ResetCache On-Premise to Cloud

AWS Storage Gateway File Gateway caches frequently accessed files. Understanding cache refresh vs reset operations is essential for maintaining data consistency.

RefreshCache
PurposeSync cache with S3 backend; detects new/modified objects
ScopeSpecific NFS share or SMB share path
OperationInventory S3 objects; update local cache index
Data Retained✓ Cached data stays; only metadata refreshed
Latency~1-5 min depending on object count
Use CaseDetect new S3 uploads; on-prem app needs latest list
ResetCache
PurposeCLEAR all cached data; full restart of cache
ScopeSpecific share or entire gateway
OperationDelete local cache files; start fresh from S3

Scenario 3: Multiple gateways in sync; one is out of date. → RefreshCache on the out-of-date gateway to resync metadata.

⚡ Exam Trap

11 CloudFront + S3 Origin: Common Issues & 307 Errors CDN & Origin Behavior

CloudFront with S3 as origin has specific behavioral quirks. Understanding redirect loops (307 errors), website endpoints vs REST API endpoints, and CORS is critical for exam scenarios.

S3 REST API Endpoint (Correct for CloudFront)
Formatmybucket.s3.amazonaws.com (or regional: mybucket.s3.us-west-2.amazonaws.com)
Use✓ CloudFront origin; native S3 API
Bucket PolicyCloudFront uses OAI (Origin Access Identity) or OAC
RedirectNone (clean); no 307

❌ S3 Website Endpoint (WRONG for CloudFront)
Formatmybucket.s3-website.amazonaws.com (website hosting)
Use✗ NOT for CloudFront; only static website hosting
Redirect✗ Triggers 307 redirect loop if used with CloudFront
ReasonWebsite endpoint redirects http → https; CloudFront re-sends
Symptom304 → 307 → 304 loop (infinite redirect)
307 Redirect Issue - Root Cause & Fix

Problem: CloudFront origin set to S3 website endpoint. Client requests https://cdn.example.com/page.html. CloudFront hits S3 website endpoint, which responds with HTTP 307 redirect (upgrade http → https, or index.html redirect). CloudFront caches 307, re-requests, loop.

Solution 1 (Recommended): Use S3 REST API endpoint (mybucket.s3.amazonaws.com), not website endpoint. CloudFront handles HTTPS; no redirect.

Solution 2: If must use website endpoint, disable caching of 307/308/301/302 redirects in CloudFront cache policy (or set TTL=0 for error responses).

Solution 3: Move index.html redirect logic to Lambda@Edge or CloudFront function (process inside CDN, avoid S3 redirect).

Scenario Correct Choice Why NOT the Alternative
CloudFront → S3 static website S3 REST API endpoint + OAI Website endpoint causes 307 redirect loops
S3 website hosting (no CDN) S3 website endpoint REST API doesn't support index.html redirection
Cross-origin JavaScript requests Enable S3 CORS + CloudFront pass-through Without CORS headers, browser blocks requests
CloudFront + Private S3 bucket OAI (deprecated) or OAC (new) + bucket policy Public bucket policy = security risk
Origin Access Control (OAC) vs Origin Access Identity (OAI)

OAI (Legacy): IAM user created in S3 backend. CloudFront signs requests as OAI user. Deprecated; AWS recommends OAC.

OAC (Current): Native CloudFront service identity. Eliminates need for separate IAM user. Simpler setup; better security model. Supports S3 POST/PUT requests (OAI didn't).

Recommendation: Use OAC for all new deployments. OAI still works but is being phased out.

⚡ Exam Trap

S3 website endpoint WRONG with CloudFront. If question mentions 307 redirect + CloudFront + S3, the issue is almost always using website endpoint instead of REST API. | OAI is legacy; OAC is current. Exam may ask about both; prefer OAC as the "modern" answer. | Must use OAI/OAC to keep S3 bucket private. If CloudFront accesses open/public S3 bucket, it's a security misconfiguration.

12 Send CloudWatch Logs to Centralized Account via Firehose Multi-Account Logging

Centralizing logs from multiple accounts to a single account is a common compliance and operational requirement. CloudWatch Logs + Kinesis Firehose is the standard pattern.

Architecture: Multi-Account Logs → Firehose

Account A (Log Source): EC2, Lambda, RDS emit logs to CloudWatch Logs.

CloudWatch Logs Subscription Filter: Pattern matches logs; sends to Kinesis Firehose delivery stream (in Account A or Account B).

Firehose Delivery Stream: Aggregates and batches logs; writes to S3 bucket (in central Account B).

S3 Bucket (Central Account B): Centralized log storage; can be analyzed by Athena, Redshift, or custom tools.

Cross-Account Setup: If Firehose destination is in separate account, IAM role must allow cross-account write.

PermissionsCloudWatch Logs role needs firehose:PutRecord
Pattern[ERROR], [WARN], or wildcard to match logs
FilteringCan filter before sending (reduce data)

Firehose Delivery Configuration

DestinationS3, Redshift, Splunk, or HTTP endpoint

Cross-Account Firehose Setup

Step 1 (Central Account B): Create S3 bucket for logs. Create IAM role that Firehose will assume (permissions: S3 write, KMS decrypt if encrypted).

Step 2 (Central Account B): Create Firehose delivery stream targeting S3 bucket. Grant role permission to write.

Step 3 (Account A): Create IAM role for CloudWatch Logs subscription. Grant permission to invoke Kinesis Firehose in Account B (cross-account).

Best Practice: Firehose vs CloudWatch Logs Insights

CloudWatch Logs Insights: For ad-hoc querying/searching; stores in CloudWatch (expensive for long-term). Firehose → S3: For archival and bulk analysis; cheaper long-term storage (~0.023/GB in S3 vs. 0.50/GB in CloudWatch). Recommended: Use both: CloudWatch Logs Insights for real-time queries; Firehose to S3 for cost-effective archival.

⚡ Exam Trap

CloudWatch Logs Subscription filters CANNOT send directly to S3. Must use Kinesis (Streams or Firehose) or Lambda as intermediary. | Cross-account Firehose requires explicit IAM trust. Don't forget Account B's Firehose role must trust Account A's CloudWatch Logs service. | Firehose batching = latency. If real-time is critical, reduce buffer size (but increases API calls/cost).

Enable Slow Query Logs - Step by Step

Step 1: Create or modify DB Cluster Parameter Group. Set slow_query_log=1. Set long_query_time=2 (threshold in seconds).

Step 2: Apply parameter group to Aurora cluster. Requires cluster restart (< 1min downtime).

Step 3: Enable "Publish to CloudWatch Logs" option in Aurora cluster. Select log types: error, general, slowquery, audit.

Step 4: Create IAM role for RDS to write to CloudWatch Logs. Trust policy allows rds.amazonaws.com. Attach AmazonRDSCloudwatchLogsRolePolicy.

Step 5: Monitor logs in CloudWatch Log Group. Query using CloudWatch Insights for performance analysis.

CloudWatch Insights Query Examples

Top 10 slowest queries: fields @timestamp, @duration | stats avg(@duration) as avg_ms by @message | sort avg_ms desc

Count errors by severity: fields severity | stats count() by severity

Connection failures in last hour: fields @message | filter @message like /refused/ or @message like /timeout/

Best Practice

Enable slow query logging with long_query_time=2-5 for production (captures actionable slow queries, not every query). Pair with CloudWatch alarms that trigger on slow query count > threshold. Use Insights for root cause analysis.

⚡ Exam Trap

Slow query logs require parameter group change + cluster restart. Can't enable them on-the-fly without downtime. | Error logs are automatic (no config). Don't need parameter changes for error log visibility. | CloudWatch Logs incurs cost. Long log retention (e.g., 1 year) = expensive. Consider archiving to S3 via Firehose.

15 X-Ray SDK: Trace HTTP Requests & SQL Queries on EC2 Distributed Tracing & Observability

AWS X-Ray SDK instruments applications to capture requests, traces, and subsegments (e.g., database queries). Understanding SDK setup, patching, and SQL tracing is critical for production diagnostics.

X-Ray SDK Setup for Java EC2 Application

Step 1: Add X-Ray SDK dependency (Maven): <dependency><groupId>com.amazonaws</groupId><artifactId>aws-xray-recorder-sdk-core</artifactId></dependency>

Step 2: Patch HTTP client (Spring Boot example):

import com.amazonaws.xray.AWSXRay; import com.amazonaws.xray.AWSXRayRecorderBuilder; import com.amazonaws.xray.plugins.ECSPlugin; import com.amazonaws.xray.strategy.sampling.LocalizedSamplingStrategy; AWSXRayRecorderBuilder builder = AWSXRayRecorderBuilder.standard() .withPlugin(new ECSPlugin()); URL ruleFile = Resources.getResource("sampling-rules.json"); builder.withSamplingStrategy(new LocalizedSamplingStrategy(ruleFile)); AWSXRay.setGlobalRecorder(builder.build());

Step 3: Configure X-Ray daemon: X-Ray daemon runs on EC2 (via port 2000 UDP) or local VPC. Agent sends traces.

Step 4: Add IAM permissions: EC2 role needs xray:PutTraceSegments and xray:PutTelemetryRecords.

X-Ray Concept: Segments vs Subsegments

Segment: Root trace of a request (e.g., incoming HTTP request to EC2). Contains metadata: host, user, request/response.

Subsegment: Child of segment; represents downstream call (e.g., to database, external API, Lambda). Nested hierarchy shows dependency chain.

Example: User hits API → Segment (incoming request). Within segment: 1) SQL query subsegment (200ms to RDS). 2) External API call subsegment (150ms to third-party). 3) Cache read subsegment (10ms to ElastiCache). X-Ray traces the full path and identifies bottlenecks.

Component Role Configuration
X-Ray Daemon (service) Collects trace segments from EC2; forwards to X-Ray service Runs on EC2 or in VPC (port 2000 UDP); IAM role on EC2 needs permission
X-Ray SDK (library) Instruments application; creates segments/subsegments Added as Maven/Gradle dependency; initialized in app startup
IAM Role (EC2) Grants EC2 permission to send traces Permissions: xray:PutTraceSegments, xray:PutTelemetryRecords
X-Ray Console Visualizes traces; shows service map & latency Query traces; filter by service, latency, error
Best Practice for SQL Tracing

1) Install X-Ray SDK with SQL support. 2) Use JDBC URL format: jdbc:xray:mysql://db.amazonaws.com:3306/mydb (wraps JDBC driver). 3) Queries are captured as subsegments within HTTP trace. 4) Use X-Ray console to identify slow DB queries across all instances. 5) Combine with Aurora slow query logs for detailed SQL analysis.

⚡ Exam Trap

X-Ray daemon must be running on EC2 (or in VPC). SDK alone doesn't send traces; daemon must exist. | IAM role is required. SDK can't send traces without xray:PutTraceSegments permission. | SQL tracing requires aws-xray-recorder-sdk-sql dependency. Core SDK doesn't trace JDBC by default. | Sampling rules control trace volume. Default may not be aggressive enough for high-traffic apps (adjust to reduce cost).
